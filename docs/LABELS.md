# 标签使用规则 / Labels

本仓库用**类型标签**说明“这是什么”，用**优先级标签**说明“多紧急”。两者独立，可以组合使用。

优先级从高到低固定为：

```text
Urgent Ultra  >  Urgent  >  High  >  Medium  >  Low
```

## 1. 优先级标签

| 标签 | 级别 | 含义 | 典型场景 | 处理目标 |
|---|---|---|---|---|
| `Urgent Ultra` | P0 | 主线或发布不可用，或会造成不可逆损失 | 游戏无法启动、存档/进度丢失、安全漏洞、`main` 持续失败且阻塞发布 | 立即处理，暂停其他工作；当天给出结论或热修 |
| `Urgent` | P1 | 当前里程碑必须完成，否则不能交付 | 核心战斗卡死、Boss 无法通关、关键流程被阻断 | 当前迭代优先，排在新功能之前 |
| `High` | P2 | 重要，明显影响体验，但存在规避办法 | 常见报错可重试、某张卡数值明显失衡、重要 UI 缺陷 | 本迭代优先排期 |
| `Medium` | P3 | 正常需求或缺陷，按计划处理 | 新卡、新敌人、普通 UI 改进、一般性重构 | 进入待办，按里程碑排期 |
| `Low` | P4 | 锦上添花或长期优化 | 文案润色、稀有场景 polish、非关键重构 | 不承诺完成时间，空闲时处理 |

### 判定规则

1. **一个 Issue / PR 最多一个优先级标签。**  
   如果出现多个，以最高级别为准，并移除其余优先级标签。

2. **没有优先级标签 = 尚未 triage，不等于 `Medium`。**  
   不要因为“看起来不严重”就默认补一个 `Medium`。

3. **优先级看影响和紧迫性，不看工作量、个人喜好或“我现在就想要”。**

4. **`Urgent Ultra` 只给真正的发布阻塞。**  
   例如无法启动、数据丢失、安全漏洞、主线不可用。普通 bug、体验问题、新功能都不能用 P0。

5. **`Urgent` 只给当前里程碑必须完成的事项。**  
   有规避办法、可以下个版本再修的，通常放 `High` 或 `Medium`。

6. **`High` 不等于“很重要所以必须现在做”。**  
   它表示本迭代应该优先，但仍需和维护者确认排期。

7. **调整优先级时在 Issue / PR 里留言说明原因。**  
   例如：`Priority: High -> Urgent，原因是 Boss 战会稳定卡死，当前版本无法通关。`

8. **PR 默认继承所关联 Issue 的优先级。**  
   只有 PR 本身独立阻塞发布时，才单独加更高优先级，并在描述里说明。

9. **关闭 Issue 时保留原标签，方便回溯。**  
   `duplicate`、`invalid`、`wontfix` 表示关闭原因，不是优先级。

### 示例

| 场景 | 建议标签 |
|---|---|
| 启动游戏立即崩溃 | `Urgent Ultra` + `bug` |
| 存档后进度丢失 | `Urgent Ultra` + `bug` |
| 某个 Boss 稳定卡死，无法通关 | `Urgent` + `bug` |
| 某张卡伤害明显过高，但可以避开 | `High` + `bug` |
| 新增一种敌人行为 | `Medium` + `enhancement` |
| 主菜单加一个动效 | `Low` + `enhancement` |
| 文档里的错别字 | `Low` + `documentation` |
| 需要作者补充复现信息 | `question`，暂不加优先级 |

## 2. 类型标签

一个 Issue 至少有一个类型标签；类型和优先级可以同时存在。

| 标签 | 用途 |
|---|---|
| `bug` | 可复现的错误行为、崩溃、数值或界面异常 |
| `enhancement` | 新玩法、新卡、新敌人、新系统或体验改进 |
| `documentation` | 文档新增、修订、纠错 |
| `question` | 信息不足，需要提问或补充 |
| `accessibility` | 影响无障碍使用的障碍 |
| `good first issue` | 维护者确认适合新人的任务 |
| `help wanted` | 需要外部协助，但维护者仍会 review |
| `try` | 实验性想法或技术验证，通常带时间盒，不承诺落地 |
| `duplicate` | 与已有 Issue / PR 重复 |
| `invalid` | 不符合范围、无法复现或信息不足 |
| `wontfix` | 明确不做 |

补充约定：

- `good first issue` 必须由维护者确认，不能作者自己加。
- `try` 只表示“可以试”，不表示已经排期。
- `duplicate` / `invalid` / `wontfix` 关闭时，尽量留言说明原因和替代链接。

## 3. 谁来设置

- 有 **Triage** 及以上权限的人可以设置标签。
- 作者可以在 Issue 中**建议**优先级，但最终以维护者 triage 为准。
- AI / 自动化代理只有在用户明确要求，或正在执行 triage 任务时，才能添加、移除或修改优先级标签。
- 代理不得批量改标签、不得新建标签、不得把 `Urgent Ultra` 当普通高优先级使用。
- 代理修改标签后，必须在回复中报告改了哪个 Issue / PR、从什么改成什么、理由是什么。

## 4. 快速检查

在给标签前问自己：

1. 这是类型标签还是优先级标签？
2. 是否已经有且只有一个优先级？
3. P0 / P1 的理由是否能写成一句话？
4. 这个优先级是否只是“我希望它快点做”？
5. 关闭原因是否应该用 `duplicate` / `invalid` / `wontfix`，而不是优先级？
