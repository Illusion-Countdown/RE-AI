## 2. 为什么 2K 下当前 1280×720 画面显低（Q1）

### 2.1 本质：有效信息量固定在 720p，不是缩放算法问题

- 逻辑画布 **1280×720 = 0.92MP**；2K 屏幕 **2560×1440 = 3.69MP**，正好 **4 倍**像素。
- 画布到窗口是 **2× 整数最近邻**，即每个逻辑像素变成 2×2 物理块。画面**清晰但不细腻**：细节上限就是 720p，符合"能看出是像素块"的观感。
- 对比：4K 全屏（k=3）会更"块"，但信息量仍是 720p —— 分辨率越高，这种"低清感"越明显。

### 2.2 为什么文字/UI 尤其显低

1. **字体是无抗锯齿小字号**：11–28px 的雅黑用 `antialias=False` 渲染出 1-bit 硬边字形，再 2× 最近邻放大 → 每个字形笔画变成 2px 宽的锯齿块。24px 中文放大到 48px 物理，看起来像"低分辨率像素字体"。
2. **1px 线条变 2px 粗条**：边框、分隔线、网格线在 2K 上全是 2px 宽，UI 显得笨重。
3. **小缓存放大**：头像 58×58 缓存 → 2K 上显示 116×116，只有 58px 级别的细节；大招立绘 58×58 → 286×286 逻辑 → 2K 572×572 物理，等于 **~10 倍上采样**，必然软。
4. **战斗精灵被主动缩过头**：640×360 源帧 → 160×90 缓存（0.25×）→ 2K 显示 320×180 物理。即使按现在的布局大小，也完全可以缓存到 320×180（0.5× 源）再放大，**现在白扔了一半的源分辨率**。
5. **程序化 UI 的"像素感"是刻意的**：`pygame.draw` 画的 1px 图形本身就是 720p 尺度的美术，放大只会变粗，不会变精致。

### 2.3 什么情况下才会"真糊/真抖"

- **1920×1080 窗口**：scale=1.5 非整数最近邻 → 像素宽度 2/1 交替（见 §3.2 与附录 A），移动镜头（战场震屏 `shake`、扫描线/噪声特效）时会出现**像素爬行/抖动**，扫描线与噪声还会产生摩尔纹。
- **任意非整数窗口**（1600×900、1366×768 等）：同上，且带黑边。
- **高 DPI 缩放**：本机实测 pygame 报告桌面 2560×1440，说明当前进程 DPI 正常；但换 125%/150% 显示缩放或换显示器后要重新用 `pygame.display.get_desktop_sizes()` 验证，否则会被 Windows 系统层拉伸（真糊）。
- 若有人把 `present()` 改成 `smoothscale`：非整数放大不抖了，但 720p 内容整体发虚，文字更糊——**换算法解决不了信息量问题**。

> 结论（Q1）：2K 下"显低"是**设计分辨率低 + 文字无抗锯齿 + 素材小缓存**三者叠加的结果。整数缩放本身是对的，要提升的是"逻辑画面的渲染精度"，不是换插值算法。

## 3. 升级到 1920×1080 / 2560×1440 逻辑档的代价与收益（Q2）

### 3.1 三条可选路线

| 路线 | 做法 | 2K 全屏 | 1080P | 改动量 | 结论 |
|---|---|---|---|---|---|
| **A. 维持现状** | 1280×720 画布 + 放大 | ×2 整数，糙但 crisp | ×1.5 非整数、略抖 | 0 | 不解决"显低" |
| **B. 逻辑档 1920×1080** | 全部 UI/坐标按 1.5× 重排，画布 1920×1080 | 若仍 canvas 放大 = **1.333 非整数**（二次重采样）→ 更差；只有直绘才可用 | 1:1，最清晰 | **高**：`main.py` 126 处 `pygame.draw`、`battle_demo.py` 190 处、94 个 `pygame.Rect` 常量、上千个字面坐标/字号全部 ×1.5 后重排；字体 11→16.5 非整数 | 单独做不划算 |
| **C. 逻辑档 2560×1440** | 全部坐标 ×2 整数 | 1:1，原生 2K | 0.75 下采样：1px 线可能消失、文字发虚 | **很高**：同上重排，且内容空间 ×4，要重新放大战场/卡面/字体来填满，否则界面显空 | 单独做不划算 |
| **D. 保留 1280 设计空间 + 按物理像素直绘（推荐）** | 设计坐标不变；渲染时统一乘 `k`：2K k=2、4K k=3；1080P 用 s=1.5 直绘（文字按原生字号渲染、坐标 round） | 文字按 22–56px **原生渲染**、线条 2px 整数、精灵缓存 320×180（0.5× 源）→ 清晰度翻倍 | s=1.5：文字原生清晰，1px 几何取整后 1–2px 略不均（可接受） | **中**：加渲染层 + 替换绘制调用（约 316 个 draw 点；字体渲染集中在 `main.py`/`battle_demo.py` 的 `text()`，battle 另有 3 处直接 `render()`），布局不用重排 | **首选** |
| E. D 之后再做 B/C | 直绘稳定后，若确实需要更多内容空间再重排 | 原生 | 原生 | 高（只做一次内容设计） | 长期可选项 |

### 3.2 非整数缩放对像素风的影响（实测）

用 4×4 棋盘格做最近邻缩放实验（脚本见附录 A）：

- **2× 整数放大**：每个像素稳定变成 2×2 块 → 像素完美。
- **1.5× 放大**：源像素宽度 2/1/2/1 交替（输出行 `##.##.`）→ 1px 线要么 1px 要么 2px、移动时爬行/抖动；1px 边框在不同坐标上粗细不一致。
- **0.75× 缩小**：直接丢像素、细节错位（`#..` / `.##`）→ 1px 线可能整条消失。
- **smoothscale 非整数**：产生中间色，硬边变软 → 像素风被破坏（本条只适用于确实要平滑的插画素材，不适用于像素 UI）。

因此像素风铁律：**位图/像素艺术只能整数倍放大（1×/2×/3×）或整数分之一缩小；只有插画类素材允许非整数 smoothscale。**

### 3.3 代价/收益结论（Q2）

- **收益**：把 2K 屏真正用起来（文字/线条/精灵细节翻倍）、4K 可到 ×3 且越清晰越明显；1080P 用户也不再是 1.5× 抖动。
- **直接改逻辑档的代价太高**：B 要 1.5× 重排（大量非整数字号），C 要 ×2 重排且 1080P 下采样；两者都要全量 UI 回归 + 重拍截图，风险远大于收益。
- **D（直绘）是性价比拐点**：不改布局、不改内容，纯渲染层改造即可在 2K 上得到"同布局但原生清晰"的画面；这是"后续迁移高分辨率"的第一步（见 §6）。
  - 性能补充：本机 dummy 驱动微基准，现有 2K 路径 `transform.scale` 1280×720→2560×1440 约 **4.1ms/帧** + blit 1.7ms；直绘省掉这 4.1ms 重采样，换成在 1440p 上直接画（基准里 200 rect + 100 文本约 2.1ms），60fps 预算内，甚至更快。真实帧率仍需在窗口模式下复测战斗特效场景。

## 4. Character Lab 的档位结论（Q3）

### 4.1 明确结论

> **Character Lab 选 1920×1080 逻辑档，按窗口物理像素直绘，默认窗口 2560×1440（s=4/3）。**
>
> 如果实现上无法直绘、只能沿用本仓库现有"固定 canvas → 整体放大"的写法，则**改选 2560×1440 逻辑档 + 默认窗口 2560×1440（1:1）**；不要用"1920 逻辑画布放大到 2560"的组合。

### 4.2 三档对比（4 个角色同屏、源帧 640×360）

| 档位 | 每角色逻辑宽 | 2K 窗口直绘后物理尺寸 | 1080P 窗口 | 评价 |
|---|---|---|---|---|
| 1280×720 | 320 | 427（0.67× 源） | 320（0.5× 源） | ✗ 太小、浪费源素材，UI/debug 信息挤 |
| **1920×1080** | **480** | **640×360（源 1:1）** | 480×270（0.75× smooth，质量好） | ✅ 推荐（前提：直绘） |
| 2560×1440 | 640 | 640×360（1:1） | 480×270（0.75×） | 直绘下与上一档同画质；固定 canvas 时这是唯一正确的组合；但 1080P 下 UI 整体缩小、坐标全按 2K 设计 |
| 2560×1440（固定 canvas 放大） | 640 | 1:1 | 0.75 canvas 下采样 | ✅ 时间紧时的次选 |
| 1920×1080（固定 canvas 放大） | 480 | 1.333 非整数 + 二次重采样 | 1:1 | ✗ 两头不讨好 |

### 4.3 为什么是 1920×1080 逻辑 + 直绘

1. **4 角色单排刚好排满 1920**：每区 480×270 逻辑；2K 窗口下 480×4/3 = **640 物理 = 源帧 1:1**，角色展示达到素材上限画质，这就是 Lab 的核心目的。
2. **1080P 屏 1:1**：按 1920 设计、1080P 窗口直绘时每个逻辑像素 = 1 物理像素，文字/边框像素完美，是通用交付画布。
3. **UI 尺度舒服**：16–24px 逻辑字号 → 1080P 16–24px、2K 21–32px，都清晰可读；1280 逻辑则 UI 太挤，2560 逻辑在 1080P 下 UI 变小。
4. **与主游戏/美术管线解耦**：Lab 是新文件，没有历史坐标包袱，用"逻辑坐标系 + 显式 scale"从第一天写对，后续也能反哺主游戏的直绘方案。

### 4.4 实现约束（给 task-9 的具体要求）

- **必须直绘**：窗口 surface 直接作为绘制目标，所有坐标/尺寸乘 `s = window_w / 1920` 后 `round()`；字体用 `round(size*s)` 现场 `font.render`；**不要**先画 1920×1080 canvas 再 `transform.scale` 到 window。
- 默认窗口 **2560×1440**（s=4/3，2K 屏满屏直绘）；`--windowed` 可用 1920×1080 调试（s=1，1080P 原生）；`--size` 任意时 `s = ww/1920`；全屏时按桌面宽度算 s 并居中/裁切策略明确。
- 若复用 `present()` 式代码，`present()` 只能做 `blit`（s=1 时）或按 s 直绘，不要再做整幅重采样。
- 2K 直绘时 `s=4/3` 为非整数：几何坐标一律 `round`，1px 边框要求"视觉均匀"就画 `max(1, round(s))` 宽；文字在物理像素尺寸下渲染（清晰），不要整数倍放大位图。
- 截图 `--shot` 输出窗口物理分辨率（2K 下 2560×1440），才能真实反映观感。

## 5. 源精灵 640×360/帧的绘制尺寸怎么选（Q4）

### 5.1 通用规则

1. **永不上采样**：绘制尺寸 ≤ 640×360（唯一例外：cut-in 大头像/立绘，但源素材本身要够大，不能用 58px 缓存硬拉）。
2. **优先 1:1**：物理绘制尺寸 = 640×360 时直接 blit（或直接从图集 subsurface copy），零重采样。
3. **下采样用 `smoothscale`**（这些是插画帧，不是像素画）；若是严格像素画素材则只用整数分之一（320×180、160×90、128×72）配最近邻。
4. **缓存尺寸 = 最终物理绘制尺寸**：不要缓存 640×360 再每帧缩，也不要缓存 160×90 再放大。
5. **动画帧按动作裁剪/抽帧可以谈**：`SPECS` 已裁掉前摇/尾部（`BATTLE.md:514-516`）。

### 5.2 Character Lab 推荐尺寸

| 场景 | 逻辑尺寸 | 2K 直绘物理 | 1080P 物理 | 缩放方式 |
|---|---|---|---|---|
| 4 个同屏（单排） | **每角色 480×270**（1920 宽正好 4 份，间隔靠源帧透明留白） | **640×360（1:1 源，零重采样）** | 480×270（0.75× smooth） | 2K：直接 copy/blit；1080P：`smoothscale` |
| 大图模式（2×2 或 3 大 1 小） | 640×360 | 853×480（1.33× 上采样，次优） | 640×360（1:1，全屏 1080P 时可用） | 仅在 1080P 用 640 逻辑 |
| 顶部切换缩略图 | 64×64 ~ 96×96 | 85~128 物理 | 64~96 | 从源帧 `smoothscale`，或单独缓存 |

- 单排 4 角色是推荐布局：**2K 下每个角色绘制目标恰好是素材原生 1:1**，这是"640×360 源帧 + 1920 逻辑 + 2560 窗口"这组数字的巧合优点（缓存尺寸可以略低于绘制目标，见 §5.4）。
- 如果以后要 8 个同屏：就会退到 320×180 逻辑（0.5×），画质下降；建议保持"4 同屏 + 顶部切换"。

### 5.3 现有战斗（`battle_demo.py`）的建议

- **现在**：保持 160×90（0.25× 源）不动，布局所限；单独把缓存改大在现有"160 逻辑 → canvas 整体 ×2"链路里**没有收益**（先缩小再放大，白费，还多一次缩放），收益只在 §6 P2 直绘之后成立。
- **将来直绘 k=2**：缓存 320×180（0.5× 源）；**k=3（4K）**：缓存 480×270（0.75× 源）。每帧物理显示尺寸 = 160×k × 90×k。
- **大招 cut-in**：目标框 330×360 逻辑 → 2K 下 660×720 物理；源头像只有 256×287，**必然上采样**。快速修复：加载时保留 256×287 原图，小图标另缩 58×58，cut-in 用原图（2K 下 ~2.6×，仍软但比现在 58→286 好一个数量级）；要真正清晰需重新生成 ≥1024×1024 头像，属于资产缺口（§6 P4）。

### 5.4 内存与加载预算（必须提前算）

单帧 640×360 RGBA = **0.88MB**；一个动作 120 帧 = **105.5MB**；一个图集（5120×5400）解码 = **105.5MB**（实测解码 152ms，抽 120 帧 32–42ms）。

| 缓存尺寸 | 单帧 | 120 帧/角色/动作 | 4 角色 × 1 动作 | 4 角色 × 2 动作（idle+move） | 备注 |
|---|---|---|---|---|---|
| 640×360（源 1:1） | 0.88MB | 105.5MB | 421.9MB | **843.8MB** | 2K 零重采样，但太重 |
| 480×270（0.75×） | 0.49MB | 59.3MB | **237.3MB** | **474.5MB** | 推荐默认档；2K 1.33× 上采样 |
| 320×180（0.5×） | 0.22MB | 26.4MB | **105.5MB** | **210.9MB** | 省内存，2K 明显软 |
| 240×135（0.375×） | 0.12MB | 14.8MB | 59.3MB | 118.7MB | 不建议用于展示 |

- 8 角色 × 4 动作 × 120 帧 × 640×360 ≈ **3.4GB** —— **绝对不要全预载**。
- 推荐策略（Lab 状态机需要 idle 与 move 两个 clip 随时可切，不能只留一个）：
  1. **只保留同屏 4 个角色**；每个角色常驻 **idle + move** 两个 clip，skill/ult 首次触发时按需加载（约 200ms，用 0.08s 交叉淡化/0.9s cut-in 遮住），LRU 上限 8–10 个 clip；切换角色时卸载离屏角色的帧。
  2. **默认缓存 480×270**：8 个 clip ≈ 474MB、上限 10 个 ≈ 593MB；2K 上画到 640×360 物理是 1.33× 上采样，插画素材肉眼差异很小。
  3. 机器内存充足且追求 2K 零重采样：对"聚焦角色"用 640×360 缓存，其余 480（4 角色 ×2 动作全 640 ≈ 844MB，不建议全量）。
  4. 内存紧张：降到 320×180（8 clip ≈ 211MB），或把 idle/move 的 120 帧抽成 60 帧（播放速度不变的做法是保留原 fps、循环变短，视觉上会"跳"，建议只对非聚焦角色用）。
  5. 图集逐张解码：`load → subsurface 抽帧 → scale 到目标尺寸 → copy → del sheet`，峰值 +105MB 瞬时，不会叠加。
- 其他：翻转（`flip`）在加载时按尺寸预计算好左右两份；不要每帧 `transform.flip`；锚点统一 `midbottom`（脚底），并按每个动作首帧 alpha 包围盒校正动作间内容偏移（不同动作裁切不同，直接用同一 midbottom 可能"跳一下"）。

## 6. 当前游戏后续迁移高分辨率的步骤（Q5）

> 原则：**设计坐标系不动，先让渲染精度上去；内容布局重排是后话。**

### P0 — 锁定口径与基线（0.5 人日）

1. 明确目标屏：主目标 **2560×1440**（本机实测），兼容 1920×1080 / 3840×2160 / 带鱼屏。
2. 用现有 `--shot` 保存 1280×720、1920×1080、2560×1440 三档截图作基线（window 尺寸=输出尺寸）。
3. 确认 DPI：`pygame.display.get_desktop_sizes()` 必须等于物理分辨率（当前实测 2560×1440 ✅）；若不等，先设 `SDL_HINT_WINDOWS_DPI_AWARENESS` 相关处理，否则系统层拉伸会真糊。

### P1 — 快速修复（0.5–1 人日，低风险、无需架构改动）

1. **加 resize/窗口事件处理**：监听 `VIDEORESIZE`（pygame 2 也有 `WINDOWSIZECHANGED`/`WINDOWRESIZED`），事件里重跑 `_update_view()`；同时处理 F11 切换后的 `view_rect` 重算。修复鼠标映射错位。
2. **统一缩放策略**：非整数比例时，严格像素风应在 `scale=floor(scale)`（1x/2x/3x）下 letterbox（牺牲满屏换像素完美）；或保留非整数但把 `transform.scale` 只在"整幅画布"用——明确写进 README，避免误以为糊。
3. **大招立绘修复**：保留 256×287 原图做 cut-in；58×58 只用于列表缩略图。零分辨率风险的画质升级。
4. **选项**：`pygame.display.set_mode(..., vsync=1)` 或 `pygame.SCALED`（GPU 缩放）作为可选模式评估，但 SCALED 仍是 720p 信息量，不解决根本问题，最多省 4ms 重采样。

### P2 — 直绘层（核心，2–4 人日）

1. 新增渲染辅助（可放 `render.py` 或 `App` 方法）：
   - `self.k`/`s = window_w / W`（全屏 = 整数 k；窗口化 = 任意 s）；
   - 坐标/矩形/线条缩放函数：`S(v)`, `R(rect)`, `line()`, `circle()` 等（统一 `round`，避免出现 0.5 物理像素）；
   - 字体缓存：`font(size)` 按 `round(size*s)` 生成/缓存；文字 `render(antialias)` 在**物理字号**下渲染。
2. 把绘制目标从 `self.canvas` 换成 `self.window`（或 `k` 倍画布），`present()` 退化为一次 blit，**删除每帧整幅 `transform.scale`**。
3. 迁移顺序：`main.py`（126 个 draw 点、1 个集中 text 入口，先把装配台/地图/商店跑通）→ `battle_demo.py`（190 个 draw 点、文字/精灵/战场层）；每屏截图对比 + 鼠标点击回归。
4. 精灵缓存尺寸随 k 走（见 §5.3）：k=2 时 320×180，k=3 时 480×270；cut-in/头像用原图。
5. 性能验收：2K 全屏 60fps；重点测 battle 满屏粒子/震屏/噪声特效。

### P3 —（可选）内容/布局放大（3–5 人日）

只有当确实需要更大战场/更多卡片信息量时才做：选定 1920×1080 或 2560×1440 设计空间，重排 §3.1 B/C 的常量，并把 2x/1.5x 像素网格规则写进美术规范（例如 2560 档要求所有美术按 2px 网格绘制，保持像素感）。这一步与 P2 不冲突：P2 先行，P3 是设计决策而非技术必需。

### P4 — 资产升级（外部依赖，非代码）

- 角色源帧 640×360 是当前展示上限；想在大屏更精致只能重新生成 960×540 / 1280×720 帧（AI 生成或重绘）。
- 头像 256×287 是 cut-in 瓶颈，建议 ≥1024×1024。
- 在此之前**不要**靠上采样假装高清（只会更糊）。

### 验收矩阵（每次改渲染层都跑）

| 窗口 | 期望 | 检查 |
|---|---|---|
| 1280×720 windowed | 1:1 与旧版逐像素基本一致 | 截图 diff、鼠标四角点击 |
| 1920×1080 windowed/fullscreen | 文字原生清晰；像素 1–2px 均匀 | 文字可读性、1px 线、无爬行 |
| **2560×1440 fullscreen（主目标）** | k=2 整数，文字 2× 原生、精灵细节提升 | 截图、战斗特效、60fps |
| 3840×2160 | k=3 | 截图、性能 |
| 3440×1440 / 21:9 | letterbox 居中不变形 | 鼠标映射、黑边 |
| 实时拖动窗口/F11 | view 与鼠标即时正确 | 交互回归 |

### 风险清单

- 直绘改造是**机械但面广**的改动（两文件合计 316 个 draw 调用点），必须分屏迁移 + 截图回归，避免坐标漏乘/重复乘。
- 非整数 s 下 1px 线条不可能处处完美（只能 round/取整宽），要接受"文字清晰、几何近似"。
- 战斗性能：1440p 满特效场景需实测，不行就把特效层留在低分辨率再放大。
- 文档/截图基线会失效一轮（所有 `--shot` 图尺寸变化），需要更新 README/BATTLE.md 的"2K 全屏 ×2 最近邻"描述。
- 主游戏若未来要支持窗口自由缩放，P2 直绘是唯一可持续方案；继续"canvas 放大"路线只会越拖越贵。

## 附录 B：本机微基准（dummy 驱动，仅供参考）

|---|---|

## 附录 D：术语

- **逻辑分辨率/设计空间**：UI 坐标所用的虚拟分辨率（当前 1280×720）。
- **物理/设备分辨率**：窗口实际像素数（2K=2560×1440）。
- **整数缩放 (integer scaling)**：物理像素 = 逻辑像素 × 整数 k；像素艺术的标准做法。
- **直绘**：不做"整幅画布重采样"，而是把逻辑坐标乘 s 后直接绘制到窗口 surface。
- **1:1（native）**：源素材像素与屏幕像素一一对应，零重采样。
